# Feature Specification: Sandbox Memory Management

**Feature Branch**: `018-sandbox-memory-management`  
**Created**: 2026-11-02  
**Status**: Draft  
**Input**: User description: "Fase 4: Sandboxing e Gerenciamento Estrito de Memória — injetar chamadas de coleta de lixo no script gerado e acionar release_cuda_memory() pós-execução"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Stable Memory Footprint During Rendering (Priority: P1)

A operator runs the pipeline to render a long approved cut. During the subprocess render execution, the generated script allocates numpy arrays and MoviePy frame buffers. Without cleanup, memory pressure may build until the process is killed by the OS. After this feature, every frame-drawing loop inside the generated script explicitly releases intermediate buffers, keeping peak RAM under 2 GB regardless of video length.

**Why this priority**: An OOM crash in the render subprocess wastes time and may corrupt output files. Preventing it is the most direct memory safety requirement of this phase.

**Independent Test**: Execute a generated render script against a ≥10-minute video cut. Monitor RSS during execution; assert peak usage stays below 2 GB and the process exits 0.

**Acceptance Scenarios**:

1. **Given** a render script generated by `coder_node` for a cut with many frames, **When** the script is executed in the isolated subprocess, **Then** peak RAM usage stays below 2 GB throughout execution.
2. **Given** `coder_node` is invoked, **When** the LLM generates the render script, **Then** the script contains explicit intermediate-buffer cleanup calls (e.g., dereferencing numpy arrays or frame objects) after each frame is processed.
3. **Given** a retry scenario after a failed render, **When** `coder_node` regenerates the script, **Then** the regenerated script still includes cleanup calls.

---

### User Story 2 - Automatic VRAM Flush After Render Subprocess (Priority: P2)

A operator's pipeline profile uses the Gemini API (GPU/CUDA mode). After the render subprocess finishes — whether it succeeded, failed, or timed out — VRAM pages allocated by the subprocess may remain pinned. After this feature, the pipeline automatically calls `release_cuda_memory()` immediately after every render subprocess exits, logging VRAM metrics to `pipeline.log` so the operator can verify reclamation.

**Why this priority**: GPU memory is a shared, scarce resource (12 GB VRAM). Leaking VRAM between render cycles blocks subsequent pipeline stages and may cause OOM on the GPU even when CPU RAM is fine.

**Independent Test**: Run two consecutive render cycles with a Gemini-profile pipeline. Inspect `pipeline.log` to confirm a VRAM-flush log entry appears after each cycle (success and failure alike), and that VRAM usage reported by the second flush is lower than what the first cycle left behind.

**Acceptance Scenarios**:

1. **Given** `execution_node` completes a subprocess with exit code 0, **When** control returns to the orchestrator, **Then** `release_cuda_memory()` is invoked and `pipeline.log` records a VRAM-flush line with before/after megabyte metrics.
2. **Given** `execution_node` subprocess fails (non-zero exit code), **When** control returns to the orchestrator, **Then** `release_cuda_memory()` is still invoked before the retry or abort routing decision is taken.
3. **Given** `execution_node` subprocess times out, **When** the `subprocess.TimeoutExpired` exception is handled, **Then** `release_cuda_memory()` is invoked in the exception handler path and logged to `pipeline.log`.
4. **Given** the pipeline is running in the Ollama/local profile (CPU mode), **When** `release_cuda_memory()` is called, **Then** the function exits silently without errors (CUDA is not initialised in that profile).

---

### Edge Cases

- **Subprocess Child Allocations**: When child processes terminate, `resource.getrusage(resource.RUSAGE_CHILDREN)` accounts for total aggregate child memory to ensure peak RSS stays < 2 GB.
- **Exception in `release_cuda_memory()`**: If `release_cuda_memory()` throws an unexpected error, `execution_node` catches the exception safely, logs a warning to `pipeline.log`, and returns the state dictionary without interrupting the orchestrator.
- **Omission during Self-Healing**: `CODER_RETRY_PROMPT_TEMPLATE` explicitly reinforces Rule 6, ensuring regenerated scripts retain `del`, `gc.collect()`, and clip closures.
- **Identical Before/After VRAM**: When VRAM difference is zero or negative (e.g. no GPU active), `freed_mb` is clamped to `0.0 MB` and logged normally without raising errors.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The `coder_node` system prompt MUST instruct the LLM to insert explicit memory management constructs (importing `gc`, dereferencing numpy arrays/temporary frame buffers in processing loops, periodic `gc.collect()`, and closing all MoviePy clips via `.close()`) in the generated render script.
- **FR-002**: The generated render script MUST keep peak RAM usage below 2 GB during execution for cuts of any duration supported by the pipeline.
- **FR-003**: The `execution_node` MUST invoke `release_cuda_memory()` (defined in `src/clipper/runtime/cuda_runtime.py`) after the render subprocess exits, unconditionally — covering success (`exit code 0`), failure (non-zero exit code), and timeout (`subprocess.TimeoutExpired`) paths.
- **FR-004**: The invocation of `release_cuda_memory()` MUST be placed in a `finally` block wrapping the subprocess execution lifecycle within `execution_node` so it fires regardless of execution outcome.
- **FR-005**: The pipeline MUST write a log entry to `pipeline.log` for each `release_cuda_memory()` invocation, recording at minimum: timestamp, cut identifier, and before/after VRAM megabyte readings (when NVML is available).
- **FR-006**: When the pipeline runs in CPU-only (Ollama local) profile, `release_cuda_memory()` MUST complete without errors or exceptions even though CUDA is not initialised.
- **FR-007**: The cleanup prompt instruction added to `coder_node` MUST also apply when the node is invoked during a self-healing retry cycle, ensuring regenerated scripts include cleanup calls.
- **FR-008**: If `release_cuda_memory()` raises an exception during cleanup, `execution_node` MUST catch it safely, log a warning to `pipeline.log`, and return the node state dictionary without disruption.

### Key Entities

- **`coder_node`**: Existing LangGraph node that generates Python render scripts via LLM (Instructor + Pydantic). Its system prompt is the point of injection for the cleanup instruction.
- **`execution_node`**: Existing LangGraph node that executes the generated script in an isolated subprocess with timeout protection. VRAM flush is added here.
- **`release_cuda_memory()`**: Existing function in `src/clipper/runtime/cuda_runtime.py` that queries NVML, triggers VRAM reclamation, and logs metrics. It must be called by `execution_node` after each subprocess cycle.
- **`CODER_SYSTEM_PROMPT`**: The string constant (or template) passed as the LLM system message in `coder_node`. This is the artefact to be updated with cleanup instructions.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Render scripts generated by the updated `coder_node` contain explicit memory management constructs (buffer release, periodic `gc.collect()`, or clip disposal), verifiable by static AST inspection of the generated file.
- **SC-002**: Executing a generated script against a 10-minute video cut with memory monitoring shows peak RSS below 2 GB at all sample points.
- **SC-003**: `pipeline.log` contains a VRAM-flush entry after every render subprocess exit (success, failure, and timeout), verifiable by log inspection in automated tests.
- **SC-004**: Zero regressions across the existing test suite (currently 234 discovered tests); all tests continue to pass after the changes.
- **SC-005**: Invocation of `release_cuda_memory()` introduces strictly less than 50ms of wall-clock overhead during `execution_node` teardown.

## Assumptions

- `release_cuda_memory()` already handles the case where NVML is unavailable (Ollama/CPU profile) by returning silently — no new behaviour is needed there beyond calling it unconditionally.
- The existing `CODER_SYSTEM_PROMPT` constant (or equivalent template) is the correct injection point; no LangGraph graph structural changes are required to carry the prompt update.
- "Intermediate-buffer cleanup" means at minimum: deleting or dereferencing loop-local numpy arrays and MoviePy frame objects within the frame-drawing loop, then calling `gc.collect()` at a configurable interval. The exact pattern is to be specified in the plan.
- The 2 GB peak RAM threshold applies to the render subprocess only, not to the total pipeline process.
- The `execution_node` already uses `subprocess.run` with `capture_output=True` and a timeout; the VRAM flush is appended inside the existing exception handling blocks.
